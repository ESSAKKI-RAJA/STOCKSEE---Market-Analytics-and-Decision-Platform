# STOCKSEE Engine & Phase Audit Report

This is a comprehensive, file-level audit of the STOCKSEE repository, covering all engines, phases, configurations, and API contracts.

## ⚠️ Executive Summary

The repository was initially heavily reliant on direct Supabase Edge Function calls from the frontend, bypassing the FastAPI backend entirely. While recent fixes have re-routed the frontend React hooks to point to FastAPI (`apiClient.ts` to `app/main.py`), several engines are running on static, heuristic, or demo fallbacks rather than production-grade ML or Database implementations. 

The application **will run locally without crashing**, but many "AI" features are explicitly stubbed or utilizing lightweight fallbacks (like VADER for sentiment) rather than the promised heavy infrastructure (FinBERT/LSTM).

### 🟡 Backend Config
- `backend/.env` **(Working)**: `ENVIRONMENT`, `LOG_LEVEL`, and `CORS_ORIGINS` correctly populated.
- `backend/app/core/config.py` **(Working)**: Correctly deserializes the `.env` variables via Pydantic `BaseSettings`.
- `backend/requirements.txt` **(Working)**: Recently updated with `yfinance` and `vaderSentiment`.
- `backend/alembic.ini` **(Fake/Demo)**: Migrations exist in config, but there are no actual SQLAlchemy models generated or tracked. The DB is disconnected from the main application flow.

### 🔴 Supabase Config
- `supabase/config.toml` **(Stubbed)**: Exists locally, but local Supabase isn't natively integrated with the FastAPI backend.
- `supabase/functions/` **(Abandoned)**: The original architecture used Edge Functions (`stock-orchestrator`, `company-profile`, `stock-analysis`), but these have been replaced by FastAPI endpoints to fulfill the offline/local-runnable requirement.

## ⚙️ Engine Status (Brim to Base)

### 1. Market Data Engine
- **File**: `backend/app/services/market_data_service.py`
- **Status**: 🟢 **Working / 🟡 Fallback-Ready**
- **Audit**: Uses `yfinance.Ticker` to pull live data. If it fails (e.g., bad symbol or no internet), it catches the exception and returns `_get_demo_history()`. It accurately normalizes open, high, low, close, and volume.

### 2. Technical Indicator Engine
- **File**: `backend/app/services/indicator_service.py`
- **Status**: 🟢 **Working**
- **Audit**: Utilizes `pandas` to calculate SMA-20, SMA-50, RSI, MACD, and historical volatility. Handles empty datasets and NaN values cleanly, returning `{"available": False}` instead of crashing.

### 3. News Engine
- **File**: `backend/app/services/news_service.py`
- **Status**: 🟡 **Stubbed / Fake**
- **Audit**: The logic to check for `FINNHUB_API_KEY` exists, but the actual HTTP fetch logic is currently a `pass` statement. It instantly drops down to returning a hardcoded, fake JSON list (`MarketFallback` and `DemoFinancial`).

### 4. Sentiment Engine
- **File**: `backend/app/services/sentiment_service.py`
- **Status**: 🟡 **Fallback Mode**
- **Audit**: VADER is implemented and actively scores the news headlines generated by the News Engine. **FinBERT is absent.** Since the News Engine returns demo news, the Sentiment Engine is effectively scoring fake data.

### 5. Prediction Engine
- **File**: `backend/app/services/prediction_service.py`
- **Status**: 🟡 **Fake / Heuristic**
- **Audit**: No ML models (LSTM/TensorFlow/scikit-learn) exist in the repository. The prediction is a hardcoded heuristic: `current_price * 1.02` for Bullish trends, `current_price * 0.98` for Bearish trends. Labeled explicitly as `Simple_Trend_Projection_Fallback`.

### 6. Signal Generation Engine
- **File**: `backend/app/services/signal_service.py`
- **Status**: 🟢 **Working (Heuristic)**
- **Audit**: Successfully aggregates Technicals and Sentiment into a composite score (0-100), yielding safe string labels (`Bullish setup`, `Neutral / wait`, `Watchlist candidate`). Does not emit dangerous "STRONG BUY/SELL" advice.

### 7. Report Engine
- **File**: `backend/app/services/report_service.py`
- **Status**: 🟢 **Working**
- **Audit**: Synthesizes quote, indicators, sentiment, prediction, and signal dictionaries into a cohesive `company_summary` JSON. Safe disclaimers are forcibly appended.

### 8. Heatmap Engine
- **File**: `backend/app/main.py` -> `GET /api/heatmap`
- **Status**: 🔴 **Fake**
- **Audit**: Hardcoded JSON array returning 4 static sectors with fake performance multipliers. No dynamic aggregation across market indices is occurring.

### 9. Watchlist/Auth Engine
- **File**: `backend/app/services/watchlist_service.py`
- **Status**: 🔴 **Fake / In-Memory**
- **Audit**: Bypasses Supabase Auth and Database RLS entirely. Uses a global Python list `_DEMO_WATCHLIST = ["AAPL", "TSLA", "MSFT"]`. Data will be lost upon Uvicorn restart.
- **Frontend Hook**: `frontend/src/hooks/useWatchlist.ts` was refactored to hit `/api/watchlist`, but `ProtectedRoute.tsx` may still rely on Supabase Auth context, potentially blocking access to the Portfolio and Watchlist pages if not bypassed.

### 10. Source/Health Logging Engine
- **File**: `backend/app/services/health_service.py`
- **Status**: 🟢 **Working**
- **Audit**: `GET /health` accurately exposes the fallback status of every internal engine to the frontend.

### 11. Frontend Visualization Engine
- **File**: `frontend/src/components/*` & `frontend/src/pages/*`
- **Status**: 🟢 **Working (with degraded UI features)**
- **Audit**: Hooks (`useStockPrices`, `useStockAnalysis`, `useCompanyProfile`) now successfully wrap `apiClient.ts` to call FastAPI. The UI renders the fallback JSON cleanly without crashing, though features relying on real authentication or real portfolio DB entries will feel disjointed.

## 🔄 Phase Audit

1. **Ingestion Phase**: Partial. Market data works via yfinance. News is stubbed.
2. **Processing Phase**: Working. Pandas easily calculates required technicals.
3. **Intelligence Phase**: Degraded. VADER works, but predictions are just mathematical heuristics.
4. **Synthesis Phase**: Working. Reports and signals safely aggregate data.
5. **Delivery/API Phase**: Working. FastAPI endpoints return standardized `FallbackResponse` Pydantic models.
6. **Visualization Phase**: Working. React components digest the API successfully.
7. **Persistence/Cache Phase**: Broken/Fake. No DB caching, no Postgres, only in-memory python lists.
8. **Auth/User Phase**: Broken. Supabase is configured in the `.env` but completely disconnected from the actual data flow.

---

## 🚨 Priority Order Fixes (What must be configured next)

To move this from a "Runnable Local Demo" to a "Production Grade Architecture":

1. **Implement Actual Finnhub News Fetching** (`news_service.py`)
   - **Why**: Currently, sentiment and reports are analyzing fake news strings. Without real news, the intelligence phase is useless.
2. **Connect SQLAlchemy / Supabase Postgres**
   - **Why**: The Watchlist is an in-memory python list. We need to define `models.py`, generate Alembic revisions, and persist user watchlists to a real `DATABASE_URL`.
3. **Sync Supabase Auth with FastAPI**
   - **Why**: The frontend uses Supabase for user auth (`AuthContext.tsx`), but the FastAPI backend has NO route protection. We need a FastAPI middleware/dependency to decode the Supabase JWT and extract the `user_id` for secure Watchlist/Portfolio operations.
4. **Build the Real ML Prediction Engine** (`prediction_service.py`)
   - **Why**: The current system multiplies the price by 1.02. This needs to be replaced by loading a trained `scikit-learn` or `Keras` model file.
5. **Implement Real Heatmap Aggregation** (`main.py`)
   - **Why**: The heatmap is hardcoded. It needs to batch-fetch top index components and calculate sector averages.
